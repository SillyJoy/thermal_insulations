# Репозиторий backend по курсу "Разработка интернет-приложений"

| №  | Метод  | URL                                         | Входные данные и результат                                                                                                                                               |
|----|--------|---------------------------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 1  | GET    | `/api/thermal_insulations?cargo_mass=4`     | Только опубликованные грузы с массой от 4 т. Без фильтра или с `0` — все опубликованные. `is_creator`: 1 для своего груза, 0 для чужого                                  |
| 2  | GET    | `/api/thermal_insulations/feed`             | Один опубликованный груз. Без параметров — первый; `?id=1` — указанный; `?id=27&next=true` — следующий по ID, после последнего снова первый. `is_liked`: личный лайк 0/1 |
| 3  | GET    | `/api/thermal_insulations/draft`            | Единственный черновик пользователя singleton. ID не передаётся. Если черновика нет — 404                                                                                 |
| 4  | POST   | `/api/thermal_insulations`                  | Создаёт черновик. Только 3 обязательных поля multipart/form-data: `insulation_name`, файл `image`, файл `video`. Ответ 201                                               |
| 5  | PUT    | `/api/thermal_insulations/{cargo_id}`       | Публикует свой черновик. Можно передать JSON с необязательными `insulation_description`, `cargo_mass`, `cargo_volume`; можно без тела. Ответ 200                         |
| 6  | DELETE | `/api/thermal_insulations/{cargo_id}`       | Мягко удаляет свой черновик или опубликованный груз. Ответ 204                                                                                                           |
| 7  | POST   | `/api/thermal_insulations/{cargo_id}/likes` | JSON `{"like": 1}` ставит личный лайк, `{"like": 0}` снимает. Автор определяется на сервере                                                                              |
| 8  | POST   | `/api/users`                                | Регистрация: JSON с `username`, `password`. ID назначается БД. Ответ 201                                                                                                 |
| 9  | POST   | `/api/authentication`                       | Заглушка, возвращает `Not implemented`                                                                                                                                   |
| 10 | POST   | `/api/deauthentication`                     | Заглушка, возвращает `Not implemented`                                                                                                                                   |

#### Лабораторная 3

- **Цель работы**: создание веб-сервиса в бэкенде нашей системы для использования его в `SPA`
- **Порядок показа**: **Скриншоты 1** Через `insomnia`/`postman` показать коллекцию 10 запросов, **Скриншоты 2-10** выполнить GET списка `услуг` (с фильтром), добавить новую `услугу` с картинкой и видео, получить поля `черновика`, опубликовать `услугу`, получить `ленту` без ид, получить ленту по ид `?next=true`, поставить `лайк`, удалить `услугу`, зарегистрировать нового `пользователя`. **Скриншоты 11-13** Показать измененные данные через `select`, **Скриншоты 14-15** объяснить модели, сериализаторы.  **Скриншоты 16-17** Показать функцию-`singleton` где пользователь указан константой и использование этой функции в методах, показать `README` с описание методов и таблиц
- **Контрольные вопросы**: веб-сервис, REST, RPC, заголовки и методы HTTP, версии HTTP, HTTPS, OSI ISO
- **Диаграмма классов** с детализацией бэкенда (домены методов по `url` с интерфейсами, перечислить все методы, модели, таблицы БД, 4 страницы фронтенда). Зависимость доменов от моделей сделать вашему коду, также указать зависимость страниц от доменов.
- **Задание**: Создание веб-сервиса со всей итоговой бизнес логикой (кроме авторизации), подключение его к БД и тестирование в `insomnia`/`postman`

Создание **веб-сервиса** для получения/редактирования данных из вашей БД. Требуется разработать все методы для реализации итоговой бизнес логики вашего приложения. Для изображений `услуг` использовать `Silo(MinIO)`. В `README` проекта описать все HTTP методы и таблицы с их полями.

**Требования к веб-сервису**

Методы и `url` в `API` должны соответствовать `REST`. Для списка `услуг` (как в 1 лабораторной) нужно предусмотреть фильтрацию на бэкенде. Взаимодействие с БД через `ORM`. Записи в статусе `удален` на клиент не передаются.

Статусы нельзя менять с любого на любой: у `создателя` два разных метода, вернуть в `черновик` нельзя. В данной лабораторной пользователь `создатель` зафиксирован во всех методах - укажите его константой через функцию-`singleton`. Системные поля (ид, статусы, создатель и модератор, даты создания, формирования и завершения) передавать с клиента для изменения запрещено. Они вычисляются на бэкенде через авторизацию и бизнес-логику. В начале адреса каждого метода добавьте `/api`

**Домен услуги:**
- GET список с фильтрацией (только опубликованные). Признак 0/1 если создатель услуги совпадает с текущим пользователем 
- GET лента (только опубликованные). Признак 0/1 если текущий пользователь лайкнул эту услугу
- GET получения черновика (не более 1 записи для пользователя), ид не указывается
- POST добавление + добавление файлов изображения и короткого видео (как файлы а НЕ просто URL), название файлов сохраняются в полях БД, а сами файлы в `Silo(MinIO)`. Названия файлов генерируются на латинице
- PUT публикации (смена статуса)
- DELETE удаление (только soft delete). Только услуги этого пользователя
- POST like (от текущего пользователя). Поле 0/1 (0 отменяет лайк, 1 ставит лайк)

**Домен пользователь:**
- POST регистрация
- POST аутентификация (заглушка для 4ой лабораторной)
- POST деавторизация (заглушка для 4ой лабораторной)
